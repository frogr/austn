## The problem

The golden set in [llm-eval-starter](https://github.com/frogr/llm-eval-starter) is 29 cases written up front, not taken from traffic. That is the right way to start. Before launch you have no traffic, so you write down the tickets you can imagine: the double charge, the outage, the sarcastic one, the prompt injection.

After launch, that set starts to lie to you. Not because the cases are wrong, but because of what is missing:

- **The head.** The most common ticket in production gets one case out of 29, so a regression on it moves the score by about 3 points. If it's 15% of your traffic, it deserves more than that.
- **The long tail.** The ticket types you didn't think of. A VAT number on an invoice. A timezone bug that looks like an account problem. A GDPR deletion request. None of them are in a set written before launch.
- **The failures.** The cases your model actually gets wrong in production are the most valuable test cases you will ever get, and they are sitting in your logs with an agent's correction attached.

So the job is to keep growing the golden set from production traffic, without filling it with copies of the same ticket, without leaking customer data into git, and without labels nobody can trust. This lesson builds that pipeline.

## The mental model

A golden set is a sample of production, biased on purpose. You want three things that random sampling won't give you: more failures than production has, more of the rare stuff than production has, and less of the head.

The pipeline has a fixed order, and the order matters:

```
logs -> scrub PII -> dedupe -> split by failure signal -> stratify -> label -> QA -> merge with provenance
incidents --------------------------------------------------------------------------------^
```

**Scrub first.** Everything after this step (dedupe keys, exports, ids, the labeling sheet, the model under test) sees scrubbed text only. If you scrub after export, the raw text has already been in a CSV on someone's laptop.

**Dedupe before sampling.** Production is repetitive. The same "reset email never arrives" ticket shows up dozens of times a week, plus resends ("Following up on this...") and copies that differ only in a greeting. If you sample first, the head eats your budget.

**Failures get a reserved share.** A ticket where an agent changed the model's category is worth ten that went fine. Reserve part of the budget for anything with a failure signal, and fill the rest from normal traffic.

**Stratify the rest.** Pick the slices you want guaranteed coverage of (here, predicted category by customer segment, plus every non-English language and every unparseable output as their own slices), give each a floor, and split the remaining budget so big slices get more, but not proportionally more.

**Label blind, label twice, adjudicate.** Labelers don't see the model's answer. A slice of items goes to two people so you can measure whether your label definitions are clear. Disagreements wait for a decision; they are never averaged.

**Every case knows where it came from.** Ids come from the scrubbed text, so the same ticket can't be added twice. Each case records its request ids, how many log lines it represents, why it was sampled, who labeled it and which version of the set it entered. The set has a version number and a hash, and both go in every eval report.

**Every incident becomes a case, the same day.** Sampling finds problems on average. Incidents are the specific failures that already cost you something.

## Worked example

The module ships a synthetic log: 500 triage requests generated by `src/generate.ts`, with realistic problems built in. There's a heavy head, a long tail, resends, names, emails, phone numbers and the occasional card number pasted into messages, and model mistakes that show up as agent overrides and thumbs-down feedback. Every log line has the fields a real app would write:

```json
{"request_id":"req_51a79ded","ts":"2026-09-01T01:28:45.182Z","feature":"triage","prompt_version":"v2",
 "model":"claude-haiku-4-5","user_id":"u_uv","user_segment":"enterprise","channel":"email","locale":"en",
 "input":"The mobile app closes itself when I try to attach a photo. Pixel 8, latest version. Call me at (039) 129-5514 if that's easier.",
 "output":{"category":"bug","priority":"high","needs_human":false,"summary":"Customer reports crash and upload."},
 "signals":{"latency_ms":922,"schema_ok":true,"user_feedback":null,"agent_override":null,"reopened":false}}
```

If your logs don't have `signals.agent_override` or something like it, that is the first thing to fix. When a support agent changes a field the model set, that's a human label on a model failure, recorded for free.

### Scrubbing

`src/pii.ts` replaces structured PII with typed, numbered placeholders:

```
before: "App crashes every time I upload a photo from my iPhone 15. Started after the latest update. You can reach me at sofia.brennan@example.com. Call me at +44 20 9317 7584 if that's easier.\n\nBest,\nSofia Brennan"
after:  "App crashes every time I upload a photo from my iPhone 15. Started after the latest update. You can reach me at [EMAIL_1]. Call me at [PHONE_1] if that's easier.\n\nBest,\n[NAME_1]"
```

Three choices in there are worth copying. Placeholders are numbered, so "I changed my email from [EMAIL_1] to [EMAIL_2]" still makes sense to a labeler and to the model. Card-like numbers are scrubbed aggressively: a false positive costs you an odd-looking test input, a false negative puts a card number in git. And the scrubber leaves alone what triage depends on. The tests pin that down:

```ts
it("keeps the details triage depends on", () => {
  const text = "Charged $49 twice on 2026-09-14 for invoice #48213, order 20260914. Chrome 128.0.6613.84, iOS 17.2, 40 users, 502 errors.";
  expect(scrubPii(text).text).toBe(text);
});
```

Regex catches structured PII. It does not catch a street address or a name in the middle of a sentence. For anything regulated, add a dedicated PII detection step and have a person look at the export.

### Sampling

Output trimmed to a few strata:

```
$ npm run golden -- sample --n 60

Read 500 log records
  PII scrubbed:        80 email, 31 phone, 9 card, 154 name
  after dedupe:        148 distinct tickets (largest cluster: 16x "I'm locked out. The reset password email never ar…")
  already in golden:   0 dropped
  failure signal:      40 tickets   no signal: 108 tickets

  pool     stratum                     available  picked
  failure  account/free                        6       3
  failure  billing/free                        6       3
  ...
  failure  lang:es                             1       1
  failure  lang:fr                             1       1
  failure  unparsed                            9       3
  normal   billing/free                       20       4
  normal   bug/free                           21       4
  ...
  normal   lang:pt                             1       1

Wrote 60 candidates to out/demo/candidates.jsonl
```

Read it from the top. 500 log lines are 148 distinct tickets: the biggest cluster is one password-reset ticket, 16 times. Dedupe uses word 3-gram shingles and Jaccard similarity after normalizing away greetings, sign-offs, resend prefixes and digits, then joins similar pairs into clusters. Two messages count as the same ticket at a similarity of 0.7. Each cluster becomes one candidate that remembers how many log lines it stands for (`occurrences`) and all of their request ids.

40 of the 148 tickets had a failure signal. They get 40% of the budget (24 items), at least one per stratum. The other 36 come from normal traffic, split across strata with a floor of 2 and square-root weighting. Square root is the useful middle ground: a stratum 100 times bigger gets 10 times the items, not 100. In the unit test, a 400-item stratum next to a 4-item one gets 37 and 3 of a 40 budget under square root; proportional gives the small one nothing.

The demo then compares this sample with picking 60 log lines uniformly at random. This comparison only works because the data is synthetic and the generator knows each request's ticket type:

```
For comparison, 60 log lines picked uniformly at random (average of 20 seeds):
                                                 uniform  this sample
  ticket types covered (of 32)                      20.9           29
  items with a failure signal                        5.8           24
  password-reset tickets (the most common type)      5.7            2
```

Same labeling budget. Four times the failures, eight more ticket types, and no labeler time spent on the sixth copy of the password-reset ticket.

### Labeling

```
$ npm run golden -- export --labelers alice,bob --overlap 0.25

Exported 60 candidates to out/demo/labels/
  sheet-alice.csv  38 rows
  sheet-bob.csv    37 rows
  15 rows are on every sheet (double-labeled for agreement)
  model output hidden; see INSTRUCTIONS.txt
```

The sheets are CSV on purpose: every labeler already has a tool that edits CSV. A labeling UI is worth building at a few thousand items a month, not at sixty. `INSTRUCTIONS.txt` goes with them and defines every field, with the priority rules spelled out ("urgent = outage, data loss, security incident") and one line that saves a lot of arguments: judge impact, not tone.

The model's answer is hidden by default. If labelers see it, they anchor on it, and you end up measuring the model against a lightly edited copy of itself. `--show-model-output` exists for the rare case where you want reviewers to correct outputs quickly, and the CLI prints "expect anchoring" when you use it.

In the demo, two simulated labelers fill the sheets: alice is careful, bob is fast and wobbles on ambiguous tickets. In real life it's you and a teammate for an hour.

### Import and label QA

```
$ npm run golden -- import

Imported labels from out/demo/labels/
  accepted 57   conflicts 3   pending 0   skipped 0   errors 0

Agreement on the double-labeled slice (n=15):
  field        agree   kappa
  category     100.0%   1.00
  priority      86.7%   0.79
  needs_human   93.3%   0.86

Conflicts (written to out/demo/labels/adjudication.csv, not merged):
  prod-2b2ce9d823  priority     alice=low  bob=medium  "Hey there, Seriously, no bulk edit in 2026? Thi…"
  prod-f87cdedf06  priority     alice=medium  bob=high  "Can someone call me about my account? - [NAME_1]"
  prod-87ffafd53e  needs_human  alice=true  bob=false  "I cancelled in August and you still billed me $…"

out/demo/golden.jsonl: v1, 57 cases (+57 added, 0 unchanged, 0 relabeled)  sha256 d8e464f3f208
```

Import validates every row and reports bad values with the file and line (`sheet-bob.csv:14: invalid label_priority "p1"`), so a typo never becomes a label.

Kappa is agreement corrected for chance. If 90% of tickets are `needs_human: false` and both labelers say false most of the time, they'll agree a lot by accident; kappa subtracts that. Lesson 2 goes deeper. For now: above 0.8 is solid, 0.6 to 0.8 means the definition has a soft spot, below 0.6 means the field isn't well defined yet and the labels aren't worth much.

Here, category is unambiguous and priority is the soft spot. Look at the conflicts: a shouty feature request (tone pulling priority up) and a vague "call me" (no stated impact). That's a finding about your instructions, not about bob. The fix is a line in `INSTRUCTIONS.txt`, like "a request with no stated impact is medium", and then the next round should agree more.

Disagreements go to `adjudication.csv` with both labels side by side. Someone decides, fills the `final_*` columns, and runs import again:

```
$ npm run golden -- import

Imported labels from out/demo/labels/
  accepted 60   conflicts 0   pending 0   skipped 0   errors 0
...
out/demo/golden.jsonl: v2, 60 cases (+3 added, 57 unchanged, 0 relabeled)  sha256 c399af6ecdb4
```

Note what didn't happen: no new version for the 57 unchanged cases, and no silent relabels. If an import proposes a different label for an existing case, it's refused unless you pass `--allow-relabel`, because a relabel moves every historical comparison that used that case.

### What a case looks like

```json
{"id":"prod-0539718a24",
 "input":"Searching for a customer by name times out about half the time.",
 "expected":{"category":"bug","priority":"medium","needs_human":false,"summary_must_mention":["slow search"]},
 "tags":["from-prod","performance"],
 "source":{"kind":"production-sample","request_ids":["req_d238cef6","req_2e3b77b2","req_91d36c17","req_949fd988"],
           "occurrences":4,"stratum":"bug/free","sample_reason":"failure:agent_override:priority",
           "added_at":"2026-10-02T09:00:00Z","golden_version":1},
 "labels":{"labelers":["alice","bob"],"adjudicated":false}}
```

Everything you'll want six months from now is there. It came from production, it stands for 4 log lines, it was sampled because an agent changed the priority, two people agreed on the label, and it entered in version 1. The `expected` block is the starter's format, so the starter's runner loads this file unchanged.

`golden.meta.json` holds the version, case count, sha256 of the file, and a history entry per version. Put the version and hash in every eval report. "Pass rate went from 88% to 91%" means nothing if the test set changed in between.

### Incidents

Say a customer writes "Great job, the update ate my invoices." The model files it as a billing question, low priority, and it sits for six hours. That's the scenario the demo uses (the log line is synthetic), and the fix starts with a test case:

```
$ npm run golden -- add-incident --from-log req_d9fc21ec --incident INC-0042 \
    --category bug --priority urgent --needs-human true --must-mention "missing data" \
    --tags "tone;ambiguous" --note "Sarcastic data-loss report classified as billing/low; sat unassigned for 6 hours."

Added inc-7e0eb18c8e for INC-0042: "Great job, the update ate my invoices. Every draft from today has dis…"
out/demo/golden.jsonl: v3, 61 cases
```

`--incident` and `--note` are required. A case without a why is a case nobody can maintain. The incident id is in the case, so when this test fails in a year, it points at the postmortem.

`add-incident` also checks for near-duplicates. If the set already holds a near-identical case, it stops and shows you that case's label, because something is off: either the existing label is wrong, or the grader passes outputs it shouldn't. Find out which before adding a second copy (`--force` exists for when you've checked).

Sarcastic data-loss tickets are 5 of the 500 log lines. The sample did pick one up, worded differently ("Love the new update. Really. All of the invoices I created this morning are gone."), so the near-duplicate check passed and the incident adds a second phrasing of the same failure. That's the right outcome. Sampling finds failure types on average; incidents add the exact wording that already cost you. You need both inputs.

### Coverage

```
$ npm run golden -- coverage

Golden set v3 (61 cases) vs 500 log records

  category         traffic  failure signals  golden  golden share
  billing            40.3%             5.6%      20         32.8%
  bug                23.5%             7.0%      14         23.0%
  account            24.7%             6.6%      14         23.0%
  feature_request     7.8%            18.4%       9         14.8%
  other               3.7%            16.7%       4          6.6%

  locale  traffic  golden
  en        96.2%      56
  es         3.0%       3
  fr         0.6%       1
  pt         0.2%       1
```

This is the table to look at before each labeling round. Feature requests are 7.8% of traffic but have the highest failure-signal rate, and the set gives them about twice their traffic share. That's the bias working as intended. Billing is under-represented relative to traffic, which is fine as long as its failure rate stays low. If it climbs, the next round's failure pool will pull more billing in on its own.

## Common mistakes

**Sampling uniformly.** You get the head over and over and almost no failures. The comparison table above is the whole argument.

**Scrubbing late.** If the raw text was ever in an export, a spreadsheet, a labeling tool or a prompt to a third-party model, scrubbing afterwards doesn't undo that. Scrub at the boundary of the logging system.

**Deduping on exact match only.** Resends and greeting variations defeat it. Normalize, then compare shingles. Check your threshold by reading a few clusters: too low and different tickets merge, too high and copies survive.

**Showing labelers the model output.** It's faster and it quietly turns your golden set into a record of what the model already does.

**One labeler, no overlap.** You can't tell a clear label definition from a consistent person. Double-label 15 to 25% until agreement is high, then you can drop it lower.

**Averaging or auto-resolving disagreements.** A disagreement is information about your definitions. Look at it.

**Relabeling in place.** Editing `expected` on an existing case moves every past comparison. Do it on purpose, record it in the history, and re-run the baseline.

**Ids from row numbers or timestamps.** Then the same ticket comes back next month with a new id, and you have two copies with possibly different labels. Derive ids from the normalized, scrubbed input.

**Tuning on everything.** If you edit prompts while looking at every golden case, the set stops being a fair test. Keep a holdout slice (the `golden_version` field makes "cases added after v5" easy to select) and look at it only to measure.

## Exercise

These use the lesson's code, which comes with the course.

1. Re-run the sample with `--weighting proportional` and then `--weighting equal`. Compare the `picked` column for `billing/free` and `lang:pt`. Which would you use if the long tail were your biggest risk? Which if billing errors cost you money?
2. Run `npm run golden -- sample --threshold 0.5` and look at the largest cluster. Then try 0.9. Read the cluster members in both cases and decide whether 0.7 is right for this data.
3. Change the priority line in `INSTRUCTIONS` (in `src/sheet.ts`) to settle the "no stated impact" case. Then change `src/simulate.ts` so bob follows the new rule on ambiguous tickets, and check that priority kappa goes up.
4. Pick a log line from `data/production-logs.synthetic.jsonl` with an `agent_override`, and add it as an incident with `--from-log`. Then try adding a resend of the same ticket with `--input` and confirm the near-duplicate check stops you.

## Check your work

- [ ] Nothing leaves the logging system unscrubbed, and your PII tests include the formats your customers actually paste.
- [ ] Dedupe runs before sampling, and you've read a few clusters to check the threshold.
- [ ] Items with failure signals get a reserved share of every labeling round.
- [ ] Every stratum you care about has a floor, including each non-English language and unparseable outputs.
- [ ] Labelers don't see model output, and a slice is double-labeled.
- [ ] You know your kappa per field, and you've changed the instructions where it's low.
- [ ] Disagreements are adjudicated by a person, never averaged.
- [ ] Case ids come from the normalized, scrubbed input.
- [ ] Every case has provenance: request ids, why it was sampled, who labeled it, which version added it.
- [ ] The golden set has a version and a hash, and both appear in every eval report.
- [ ] Every production incident becomes a case with the incident id and a note.
- [ ] You run a coverage report before each labeling round.
